>
> | | 인코딩 | 왜 |
> |---|---|---|
> | 내보내기 | `utf-8` | 표준. 군더더기 없음 |

>
> **엑셀로 편집한 파일을 가져오는 게 가장 흔한 사용 패턴**인데,
> 그냥 `utf-8`로 두면 거기서 깨집니다. 실제로 겪어서 바꿨습니다.
>
> `newline=""`도 중요합니다. 파이썬 `csv` 모듈은 줄바꿈을 자기가 처리하는데,
> 이걸 안 주면 **윈도우에서 빈 줄이 하나씩 끼어** 들어갑니다."

| | `Repository` | `BudgetService` |
|---|---|---|
| 아는 것 | 파일 경로, JSONL 한 줄 형식, 원자적 교체 | 예산 초과 판정, 월별 집계, 검색 조건 |

> "예를 들어 '예산 90% 넘으면 경고'라는 규칙은 **파일과 아무 상관이 없습니다.**
> 그래서 Service에 둡니다. 반대로 '임시 파일에 쓰고 바꿔치기한다'는

## 2-3. 파일 기반 update/delete를 안전하게 처리한 방법 ★ 이 항목의 핵심

> "JSONL은 **한 줄만 고칠 수가 없습니다.** 길이가 달라지면 뒤가 전부 밀리니까요.
> 그래서 **전체를 다시 쓰는데**, 그냥 덮어쓰면 쓰는 도중에 전원이 나가면
> **원본도 새 데이터도 없는 상태**가 됩니다.
>
> 그래서 **원자적 교체(atomic replace)**를 씁니다. `repository.py`의 `rewrite()`입니다."

```python
1. 같은 폴더에 임시 파일을 만들어 전부 쓴다
2. os.fsync()    — OS 버퍼가 아니라 디스크에 진짜 내려갔는지 보장
3. os.replace()  — 임시 파일을 원본 자리로 '원자적으로' 교체
```

**세 가지 디테일을 꼭 말하세요**

| 디테일 | 이유 |
|---|---|
| **같은 폴더**에 임시 파일 | `os.replace`의 원자성은 **같은 파일시스템 안에서만** 보장됨 |
| **`os.fsync()`** | 안 하면 "썼다"고 해도 **OS 버퍼에만** 있을 수 있음. 전원이 나가면 날아감 |
| **`os.replace()`** | 파일시스템 수준에서 **한 번에** 바뀜. 중간 상태가 없음 |

> "그래서 **어느 시점에 죽어도 '완전한 예전 파일' 아니면 '완전한 새 파일'** 둘 중
> 하나입니다. **반쯤 쓰인 파일은 생기지 않습니다.**
>
> 그리고 `items`를 **제너레이터로 받기** 때문에, 전체를 다시 쓰는 과정에서도
> **메모리에 전부 올라오지 않습니다.**"

## 3-1. 제너레이터 스트리밍 ★ 이 미션의 핵심

**어떻게**

> "`return` 대신 **`yield`**를 씁니다. 리스트를 만들어 한 번에 돌려주는 게 아니라,
> **한 건 읽을 때마다 바로 넘겨주고** 다음 호출 때 멈춘 자리에서 이어갑니다."

```python
def stream(self, flt=None):
    with open(self.path, encoding="utf-8") as f:
        for line in f:                 # 한 줄씩
            tx = Transaction.from_json(line)
            if flt is None or flt.matches(tx):
                yield tx               # 여기서 넘기고 멈춤
```

**왜 유리한가 — 숫자로 말하세요**

```bash
python3 ../02_과제2-1_평가준비/스트리밍_시연.py
```
```
리스트 방식 : 60.08 MB
스트리밍    :  0.05 MB     ← 1,200배 차이
```

> "거래가 몇 건이든 **메모리에는 항상 한 건만** 올라갑니다.
> 10만 건이어도 10건일 때와 메모리 사용량이 같습니다."

### ★ 가장 날카로운 꼬리 질문: "최신순이 필요한데, 정렬하려면 결국 다 모아야 하지 않나요?"

> "맞습니다. 그래서 **전부 모으지 않고 상위 N개만 유지**합니다.
> `heapq.nlargest(limit, self.stream(flt), key=...)`를 씁니다.
>
> 힙에 **limit개만** 들고 돌면서, 새 값이 힙의 최솟값보다 크면 교체합니다.
> 메모리는 **O(limit)**이지 O(n)이 아닙니다.
> 전체 정렬이 O(n log n)인데 이건 **O(n log limit)**이라 더 빠르기도 합니다."

## 3-2. 데코레이터로 분리한 공통 기능

> "세 가지를 분리했습니다. 전부 **'업무와 상관없지만 모든 명령에 필요한 것'**입니다."

| 데코레이터 | 하는 일 | 왜 분리했나 |
|---|---|---|
| `@handle_errors` | 예외를 `[오류]`+`[힌트]`로 바꾸고 종료 코드 설정 | 12개 명령마다 try/except면 **같은 코드가 12번** |
| `@log_call` | 명령 이름·인자를 로그에 남김 | 감사 추적이 필요한데 본문에 섞이면 읽기 어려움 |
| `@timed` | 실행 시간 측정 (`--verbose`) | 성능 확인용. 평소엔 꺼둬야 함 |

> "이런 걸 **'횡단 관심사(cross-cutting concern)'**라고 합니다.
> 기능을 가로질러 모든 곳에 필요한 것이죠. 본문에 섞어두면
> ① 같은 코드가 반복되고 ② **진짜 업무 로직이 안 보입니다.**
> 분리하면 `add()` 함수를 열었을 때 **'거래를 추가한다'는 일만** 보입니다."

### ★ 꼬리 질문: "쌓는 순서에 의미가 있나요?"

> "있습니다. **아래에서 위로 감싸집니다.**"

```python
@handle_errors   # ③ 가장 바깥 — 모든 예외를 최종적으로 잡는다
@log_call        # ②
@timed           # ① 가장 안쪽 — 실제 함수에 가장 가깝다
def add(...):
```

> "`@handle_errors`가 **맨 위에 있어야** 안쪽에서 난 예외를 전부 잡을 수 있습니다.
> 순서를 뒤집으면 `log_call`에서 난 예외는 못 잡습니다."

### ★ `functools.wraps`는 왜?

> "데코레이터로 감싸면 함수의 **이름과 docstring이 래퍼 것으로 바뀝니다.**
> `add.__name__`이 `'wrapper'`가 되어버려요. `@wraps`는 **원래 정보를 복사**해
> 그걸 막습니다. 안 쓰면 디버깅할 때 모든 함수가 `wrapper`로 보입니다."

## 3-3. 타입 힌트의 이점을 어떻게 확인했나

**어떻게 확인했나 — 이게 질문의 핵심입니다. 도구를 돌려보세요**

```bash
python3 -m mypy budget_app/     # 없으면: pip install mypy
```

> "타입 힌트는 **실행에 영향을 주지 않습니다.** 파이썬은 그냥 무시해요.
> 그래서 **도구로 검사해야 의미가 있습니다.**"

| 이점 | 예시 |
|---|---|
| **실행 전에 오류를 잡는다** | `latest(limit: int)`에 문자열을 넘기면 돌려보기 전에 경고 |
| **문서가 된다** | `def search(flt: SearchFilter) -> Iterator[Transaction]` 한 줄이 주석 세 줄보다 명확 |
| **에디터가 자동완성** | 반환 타입을 알아야 `.`을 찍었을 때 후보가 뜸 |

```python
TxType = Literal["income", "expense"]      # 두 값만 허용 — 오타를 미리 잡는다
def stream(...) -> Iterator[Transaction]:  # list 가 아니라 Iterator → 스트리밍임을 타입으로 선언
```

> "`-> Iterator[Transaction]`라고 써두면 **'이건 리스트가 아니라 한 번만 돌 수 있는
> 흐름이다'**가 타입에 드러납니다. 두 번 돌리면 비어 있는 이유를 **타입만 보고** 알 수 있어요."

# 🟦 항목 4 — 설계 판단 (가장 어려운 항목)

## 4-1. JSONL과 CSV 중 왜 JSONL을 택했나

| | **JSONL** (택함) | CSV |
|---|---|---|
| 한 줄 = 한 레코드 | ✅ | ✅ |
| **중첩 구조** (`tags: [...]`) | ✅ 그대로 표현 | ❌ 따옴표로 욱여넣어야 함 |
| 필드 추가 | ✅ 기존 줄 **안 고쳐도 됨** | ❌ 헤더·모든 줄 수정 |
| 타입 보존 | ✅ 숫자/문자/배열 구분 | ❌ **전부 문자열** |
| 사람이 읽기 | 보통 | ✅ 좋음 |
| 엑셀 호환 | ❌ | ✅ |

> "**결정적이었던 건 `tags`였습니다.** 한 거래에 태그가 여러 개 달리는데,
> CSV로는 `"meal,lunch"`처럼 한 칸에 욱여넣어야 하고 읽을 때 또 쪼개야 합니다.
> **쉼표가 든 태그가 있으면 깨집니다.** JSONL은 배열을 그대로 씁니다.
>
> 그리고 **타입이 보존**됩니다. CSV에서 `amount`를 읽으면 `"8500"` 문자열이라
> 매번 int로 바꿔야 하는데, JSONL은 숫자로 그대로 나옵니다.
>
> 다만 **CSV를 버린 건 아닙니다.** import/export는 CSV로 지원합니다.
> **내부 저장은 JSONL, 외부 교환은 CSV** — 엑셀로 열어야 하는 건 사람이니까요."

## 4-2. ★ 거래가 10만 건이 되면 병목은 어디인가

> **세 병목을 순서대로 말하세요.**

**병목 ① update/delete의 전량 재작성 — 가장 먼저 터집니다**

> "지금은 한 건을 고쳐도 **10만 줄을 전부 다시 씁니다.** O(n) 쓰기예요.
> 거래 하나 수정에 수십 MB를 쓰게 됩니다. **이게 제일 심각합니다.**"

**병목 ② 검색이 전체 스캔**

> "제너레이터라 **메모리는 괜찮지만**, 조건에 맞는 게 1건이어도 **10만 줄을 다 읽습니다.**
> 인덱스가 없으니까요. 메모리 문제가 아니라 **디스크 I/O 문제**입니다."

**병목 ③ summary도 매번 전체 스캔**

> "월별 요약을 볼 때마다 10만 건을 다시 집계합니다."

**개선 방향 — 현실적인 순서로**

| 순위 | 개선 | 해결하는 병목 |
|---|---|---|
| 1 | **SQLite로 전환** | ①②③ 전부. `date`·`category`에 인덱스를 걸면 검색이 O(log n), update는 그 줄만 |
| 2 | 월별 파일 분할 (`2026-10.jsonl`) | ①② — 한 달치만 읽고 쓰면 된다 |
| 3 | append-only + 주기적 compaction | ① — 수정을 '덧붙이기'로 기록하고 나중에 정리 |
| 4 | 월별 요약 캐시 | ③ — 지난 달 집계는 변하지 않으니 저장해둔다 |

> "**1번이 정답이지만**, 이 미션은 '파일 입출력을 직접 다뤄보는 것'이 목적이라
> 일부러 DB를 안 썼습니다. 10만 건이 되면 **그 목적이 끝난 시점**이니
> SQLite로 옮기는 게 맞습니다. 마침 다음 미션(B6-1 디지털 서랍장)이 그걸 다룹니다."

## 4-3. ★ import CSV에 깨진 행이 섞이면 어떻게 신뢰를 지킬 것인가

> 알려주면 사용자가 **그 줄만 고쳐서 다시 넣을 수 있습니다.**
>
> 신뢰는 '실수를 안 하는 것'이 아니라 **'실수를 숨기지 않는 것'**에서 나온다고 생각했습니다."

# 🟦 마지막 — "경험 정도 (재구현 가능 여부)"

평가표 맨 아래에서 평가자가 **"이 사람이 다시 만들 수 있을까"** 를 체크합니다.
**항목 1~5와 따로 매겨집니다** — 항목을 다 맞혀도 여기서 깎일 수 있습니다.

이 미션은 커밋이 세 개뿐이라 "버그를 고친 기록"이 많지 않습니다. 대신
**설계하면서 막혔다가 푼 지점**이 코드 주석에 남아 있습니다. 그게 더 좋은 재료입니다.

**① "최신순"과 "스트리밍"이 서로 모순이었다 — 이 미션 최고의 이야깃거리**

`budget_app/services.py` 의 `latest()` 함수입니다. 주석에 그 고민이 그대로 적혀 있습니다.

> "거래가 많아져도 메모리를 덜 쓰려고 **제너레이터로 한 건씩 흘려보내게** 만들었습니다.
> 그런데 `list --latest 10`을 붙이려니 **막혔습니다.**
> **'최신순'이려면 정렬을 해야 하는데, 정렬하려면 결국 전부 모아야 하지 않나?**
> 그러면 스트리밍한 의미가 없어집니다.
>
> `heapq.nlargest`로 풀었습니다. 이건 **스트림을 한 건씩 받으면서 크기 N짜리 힙만
> 유지합니다.** 10만 건을 읽어도 **메모리에 동시에 있는 건 N건뿐입니다.**
> 전부 모아서 정렬하는 것과 결과는 같은데 메모리는 전혀 다릅니다.
>
> 정렬 기준을 `(date, id)` 두 개로 둔 것도 겪어서 알았습니다. **날짜만으로 하면
> 같은 날짜 거래들의 순서가 들쭉날쭉했습니다.** id는 등록 순서대로 늘어나니까,
> 같은 날 안에서는 나중에 넣은 것이 위로 옵니다."

> 💡 평가자가 **"정렬하려면 다 모아야 하지 않나요?"** 라고 물으면 이 미션에서
> 가장 날카로운 질문입니다. 위 답이 준비돼 있으면 거기서 점수가 갈립니다.

**② 파일 한가운데 한 줄만 고칠 수 없다는 걸 알았다**

`budget_app/repository.py` 맨 위 주석입니다.

> "`update`와 `delete`를 만들려니 **파일 한가운데 한 줄만 고치는 게 불가능**했습니다.
> 길이가 달라지면 뒤 내용이 전부 밀리기 때문입니다. 결국 **전체를 다시 쓸 수밖에** 없었습니다.
>
> 그런데 원본에 바로 덮어쓰다가 **중간에 프로그램이 죽으면 데이터가 반쯤 날아갑니다.**
> 그래서 ① **같은 폴더에** 임시 파일을 만들고 ② 거기 다 쓰고 `os.fsync`로 디스크에
> 확실히 내려쓴 뒤 ③ `os.replace`로 원본 자리에 밀어 넣습니다.
> **그 마지막 한 순간만 원자적(atomic)입니다** — 성공 아니면 실패 둘 중 하나고,
> '반쯤 쓰인 파일'이 남지 않습니다.
>
> **같은 폴더여야 하는 이유**도 겪어서 알았습니다. 다른 폴더면 디스크가 달라질 수 있고,
> 그러면 `os.replace`가 원자적이지 않습니다."

**③ 엑셀이 파일 앞에 안 보이는 글자를 붙인다**

> "내보낸 CSV를 엑셀로 열어 저장하고 다시 읽어오니 **첫 컬럼명이 깨졌습니다.**
> 엑셀이 파일 맨 앞에 **BOM이라는 안 보이는 표식**을 붙여서, `date`가
> `\ufeffdate`가 되어 있었습니다.
>
> **쓸 때는 `utf-8`, 읽을 때는 `utf-8-sig`** 로 다르게 둬서 해결했습니다.
> `utf-8-sig`는 그 표식이 있으면 떼고 읽습니다. 그리고 `newline=""`도 같이 넣었습니다 —
> 없으면 윈도우에서 **빈 줄이 한 줄씩 끼어듭니다.**"

**덧붙이면 좋은 것 — "일부러 안 했습니다"**

> "**데이터베이스를 일부러 쓰지 않았습니다.** 파일로 하면 **사용자가 자기 데이터를
> 직접 열어볼 수 있습니다.** 용돈 기입장은 '내 돈이 어디 갔나'를 보는 도구니까
> 그게 더 맞다고 봤습니다. 10만 건이 되면 DB로 가야 하지만, **그 시점은 이미
> 이 프로그램의 목적이 끝난 시점**입니다."

> 💡 **"알고도 이렇게 선택했다"를 말할 수 있으면** 재구현 가능한 사람으로 보입니다.
> 몰라서 안 한 것과 알고 안 한 것은 완전히 다르게 들립니다.
